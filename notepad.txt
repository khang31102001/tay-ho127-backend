3. Customer Authentication

Customer phải hỗ trợ 2 phương thức đăng nhập:

Method 1 — Local Account

Flow:

Register
→ Login
→ Access Token
→ Refresh Token
→ Authenticated Customer

Register tối thiểu hỗ trợ:

Full Name
Phone
Email
Password

Password:

tuyệt đối không lưu plain text;
sử dụng password hashing theo security pattern hiện tại.
Method 2 — Google Login

Flow:

Google OAuth
→ Verify Google identity/token
→ tìm Customer hiện tại
→ nếu chưa tồn tại thì tạo Customer
→ nếu đã tồn tại thì liên kết identity
→ phát hành Access Token / Refresh Token của hệ thống.

Không sử dụng Google token làm session token chính của application.

4. Auth Persistence Design

Database hiện tại chưa thể hiện password/provider credentials.

Hãy phân tích architecture hiện tại và thiết kế phần persistence cần thiết cho Customer Auth.

Ví dụ có thể cần:

customer_auth_identities

hoặc cấu trúc tương đương:

id
customer_id
provider // local | google
provider_user_id
email
password_hash // local only
created_at
updated_at

Nếu architecture hiện tại đã có Auth Identity/Credential pattern có thể reuse thì ưu tiên reuse.

KHÔNG tự ý thêm field password trực tiếp vào customers nếu architecture không phù hợp.

Nếu cần thay đổi Database Schema:
→ báo cáo thay đổi trước khi tạo migration.

5. Account Linking

Xử lý trường hợp:

Customer đăng ký bằng Email/Password
sau đó Login Google bằng cùng email.

Không tự động tạo duplicate Customer.

Phân tích và implement rule an toàn để:

Local Account
+
Google Identity
↓
same Customer

Phải tránh Account Takeover.

6. Token / Session

Reuse Auth infrastructure hiện tại nếu phù hợp:

JWT
Access Token
Refresh Token
Token expiration
Refresh Token rotation/revocation
Logout.

Customer JWT phải có identity rõ ràng, ví dụ:

sub
customer_id
account_type = customer

Không đưa Admin Role/Permission vào Customer nếu không cần.

7. Security Boundary

Phải đảm bảo:

Customer Authentication
≠
Admin Authentication

Customer token không được truy cập Admin API.

Admin token không tự động được coi là Customer.

Nếu dùng chung JWT infrastructure thì phải có cơ chế phân biệt:

account_type
hoặc
audience
hoặc security mechanism tương đương theo architecture hiện tại.
